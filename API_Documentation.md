# LAN-Based Distributed Compute System — API Reference

**Scope:** This document specifies every network-facing and process-facing interface in the system at implementation depth: wire formats, field-by-field schemas, default ports, error semantics, and worked examples. It covers four distinct APIs that together make up the platform:

| # | API | Transport | Parties |
|---|-----|-----------|---------|
| 1 | Discovery Protocol | UDP broadcast | Worker → Master |
| 2 | Control Plane API | gRPC (HTTP/2 + Protobuf) | Master ↔ Worker |
| 3 | Client API | REST (HTTP/JSON) + WebSocket | Client Dashboard ↔ Master |
| 4 | Data Plane Contract | SMB/NFS shared filesystem | Master ↔ Worker (file I/O, not RPC) |

Each section gives the endpoint/RPC, its parameters, a worked request/response example, error codes, and — where a design decision was made — the alternative that was rejected and why. If you implement exactly what's below, the three tiers (Client, Master, Worker) described in the architecture doc will interoperate with no further design decisions required.

---

## 0. Global Conventions

- **Default ports:** UDP discovery `5005`, gRPC control plane `50051`, REST/WebSocket API `8080`.
- **IDs:** All entity IDs (`job_id`, `subtask_id`, `worker_uuid`) are UUIDv4 strings, generated by whichever side creates the entity (Master creates `job_id`/`subtask_id`; Worker creates its own `worker_uuid` on first boot and persists it locally so identity survives restarts).
- **Timestamps:** All timestamps are Unix epoch milliseconds, integers, UTC. Not ISO-8601 strings — this avoids timezone-parsing bugs on Windows workers and keeps telemetry comparisons to cheap integer subtraction (telemetry math happens dozens of times per second per node; string timestamps would force a parse on every scheduling pass).
- **Encoding:** REST payloads are UTF-8 JSON. gRPC payloads are Protobuf binary (proto3). UDP payloads are UTF-8 JSON (small, human-debuggable with `tcpdump -A`, and there's no throughput pressure on discovery traffic to justify binary encoding there).
- **Versioning:** REST routes are prefixed `/api/v1/...`. The gRPC service is named `ComputeServiceV1`. Bump the version segment on any breaking change; do not silently mutate v1 semantics, because Workers and the Dashboard are deployed independently and will run mismatched versions during rollout.

## 1. Discovery Protocol (UDP)

### 1.1 Why UDP broadcast instead of mDNS/Zeroconf

mDNS (Bonjour/Avahi) is the obvious first choice for zero-config discovery, but it was rejected for three concrete reasons:

1. **Cross-platform reliability is inconsistent.** Avahi (Linux), Bonjour (macOS), and Windows' mDNS responder behave differently under corporate/managed network policies, and Windows often has the mDNS responder disabled or firewalled by default on domain-joined machines. A raw UDP broadcast requires zero OS services beyond a socket.
2. **We need a custom payload on the very first packet** (worker capabilities, OS type) so the Master can pre-filter before a TCP/gRPC handshake even happens. mDNS service records (TXT records) are size-constrained (~255 bytes per string) and require DNS-SD boilerplate to carry structured JSON; a raw UDP datagram just carries the JSON directly.
3. **Simplicity of implementation.** mDNS requires a client library (`zeroconf`, `python-avahi`) with platform-specific quirks; raw UDP is `socket.socket(AF_INET, SOCK_DGRAM)`, ~15 lines, identical on every OS.

The tradeoff we accept: UDP broadcast doesn't cross subnet boundaries (mDNS with reflectors can, in theory). This is acceptable because the system's explicit design target is a single flat LAN segment (home/small-office), not routed multi-subnet networks.

### 1.2 Message 1 — `DISCOVERY_BEACON` (Worker → Master)

- **Direction:** Worker broadcasts, does not target a specific IP (destination `255.255.255.255:5005`).
- **Frequency:** Sent once on worker startup, then retried every 5s until a `MASTER_OFFER` is received, then stopped. If the worker later loses its gRPC connection to the Master (see §2.6 heartbeat timeout), it re-enters beacon mode automatically.

**Payload schema:**

| Field | Type | Required | Description |
|---|---|---|---|
| `type` | string (const) | yes | Always `"DISCOVERY_BEACON"`. Lets a single UDP listener socket demux beacon vs. offer if both roles run on one dev machine. |
| `protocol_version` | int | yes | `1`. Master rejects beacons with a version it doesn't support and logs a warning rather than silently dropping (silent drops are the #1 cause of "why won't my node join" support requests). |
| `worker_uuid` | string (UUID) | yes | Persisted locally at `~/.lan-compute/worker_id` (Linux/macOS) or `%APPDATA%\lan-compute\worker_id` (Windows). Generated once, reused across restarts so the Master's Node Registry can recognize a returning node instead of treating it as new. |
| `local_ip` | string | yes | The worker's own best-guess LAN IP (from the socket used to send the UDP packet — do NOT trust `socket.gethostname()` resolution, which is unreliable on multi-homed machines). |
| `os_type` | enum string | yes | One of `"windows"`, `"linux"`, `"macos"`. Determines which virtualization layer (WSL2 / Podman / Metal sandbox) the Master expects this node to run. |
| `hostname` | string | no | Human-readable, shown in the dashboard node list. Falls back to `worker_uuid[:8]` if omitted. |

**Example packet:**
```json
{
  "type": "DISCOVERY_BEACON",
  "protocol_version": 1,
  "worker_uuid": "8f14e45f-ceea-4a3d-8f1b-3d2f6a1c9b90",
  "local_ip": "192.168.1.102",
  "os_type": "linux",
  "hostname": "fedora-workstation"
}
```

### 1.3 Message 2 — `MASTER_OFFER` (Master → Worker, unicast reply)

Sent as a unicast UDP reply to the source IP:port of the beacon (do not broadcast the offer — with multiple workers on the LAN, broadcasting offers causes every worker to log noise about offers not addressed to it, and on larger LANs it's needless traffic).

| Field | Type | Required | Description |
|---|---|---|---|
| `type` | string (const) | yes | `"MASTER_OFFER"` |
| `protocol_version` | int | yes | Must match the beacon's version; if it doesn't, the worker logs a version-mismatch error and does not proceed to gRPC registration (fail loud, not silent). |
| `master_uuid` | string (UUID) | yes | Identifies this Master instance — relevant if a worker was previously paired to a different Master and needs to detect a switch. |
| `grpc_uri` | string | yes | e.g. `"192.168.1.100:50051"`. Sent explicitly rather than assumed-from-source-IP because the Master's UDP listener IP is not guaranteed to be the same interface as its gRPC bind IP on multi-homed machines. |
| `cluster_token` | string | no | Optional shared secret (see §5, Security). Empty string if the cluster is running with the current default of "trusted LAN, no auth." |

**Example packet:**
```json
{
  "type": "MASTER_OFFER",
  "protocol_version": 1,
  "master_uuid": "1a2b3c4d-5e6f-7890-abcd-ef1234567890",
  "grpc_uri": "192.168.1.100:50051",
  "cluster_token": ""
}
```

### 1.4 Post-discovery handoff

Upon receiving a valid `MASTER_OFFER`, the worker immediately opens a gRPC channel to `grpc_uri` and calls `RegisterWorker` (§2.2). The UDP exchange's only job is IP/port discovery — all further interaction, including the "real" handshake, happens over gRPC. This split matters: UDP is unreliable/unordered, so nothing that requires a guaranteed response (like actual registration) should live in the UDP payload itself.

## 2. Control Plane API (gRPC)

### 2.1 Why gRPC instead of REST for Master↔Worker

- **Bidirectional streaming.** Telemetry is a continuous push (worker → master, several times a second) combined with a continuous push in the other direction (master → worker control signals like pause/cancel). REST has no first-class bidirectional stream; you'd need to fake it with long-polling or a second WebSocket, doubling the connection count per worker.
- **Binary framing over HTTP/2 multiplexing.** With up to dozens of workers each holding an open telemetry stream, HTTP/2 multiplexes all RPCs for a worker over a single TCP connection, versus REST/HTTP1.1 which would need connection-per-request or a manually managed keep-alive pool.
- **Schema enforcement.** Protobuf gives compile-time-checked message contracts across three languages' worker agents (Python master, and worker agents that may eventually be reimplemented in Go/Rust for lower overhead) — a JSON REST contract only enforced by convention is a much easier place for the Windows worker and Linux worker to silently drift apart.

The tradeoff: gRPC is harder to debug with a browser or `curl` than REST. This is why the **client-facing** API (§3) is deliberately kept as plain REST — humans and browser tooling touch that one; only worker agents and the Master talk gRPC.

### 2.2 Proto Definition (canonical, full)

```protobuf
syntax = "proto3";
package computeservice.v1;

service ComputeService {
  // Worker → Master, unary. First contact for a NEVER-BEFORE-SEEN worker_uuid.
  // Master generates a PIN, shown on the Master's own console/dashboard.
  rpc InitiatePairing (PairingRequest) returns (PairingChallenge);

  // Worker → Master, unary. Called once the laptop's owner has typed the
  // PIN (that they were told by the Master's operator) into the worker
  // agent's tray prompt. Success returns a persisted worker_token.
  rpc ConfirmPairing (PairingConfirmation) returns (RegistrationStatus);

  // Worker → Master, unary. Called on every subsequent boot using the
  // worker_token from a prior ConfirmPairing — no PIN required again.
  rpc RegisterWorker (WorkerInfo) returns (RegistrationStatus);

  // Either side, unary. Permanently invalidates a worker_token — either
  // the friend revoking access from the worker tray app, or the Master's
  // operator removing a device from the dashboard. See 2.4a.
  rpc UnpairWorker (UnpairRequest) returns (UnpairAck);

  // Worker → Master, unary. Graceful leave (Ctrl+C, shutdown, sleep).
  rpc UnregisterWorker (UnregisterRequest) returns (UnregisterAck);

  // Master → Worker, unary. Dispatches one fragment for execution.
  rpc SubmitSubTask (TaskPayload) returns (TaskAck);

  // Worker → Master, unary. Request to abort by subtask_id.
  rpc CancelSubTask (CancelRequest) returns (CancelAck);

  // Worker → Master, unary. Reports terminal state of a subtask.
  rpc ReportSubTaskResult (SubTaskResult) returns (ResultAck);

  // Worker → Master, BIDIRECTIONAL STREAM.
  // Worker streams NodeHealth continuously; Master streams
  // ControlSignal back on the same call (e.g. THROTTLE, RESUME, ABORT).
  rpc StreamTelemetry (stream NodeHealth) returns (stream ControlSignal);
}

// ---- Registration ----

message WorkerInfo {
  string worker_uuid = 1;
  string hostname = 2;
  string os_type = 3;          // "windows" | "linux" | "macos"
  string os_version = 4;       // e.g. "Fedora 44 (6.9.14)"
  HardwareProfile hardware = 5;
  string worker_token = 6;     // "" on InitiatePairing; required on RegisterWorker after pairing
}

message HardwareProfile {
  string cpu_model = 1;
  int32 cpu_cores_physical = 2;
  int32 cpu_cores_logical = 3;
  repeated string cpu_instruction_sets = 4;  // ["AVX2","AVX-512","AMX"]
  float ram_total_gb = 5;
  bool has_gpu = 6;
  string gpu_model = 7;                      // "" if has_gpu = false
  float vram_total_gb = 8;
  repeated string hw_encoders = 9;            // ["NVENC","QuickSync"]
  string virtualization_mode = 10;            // "podman" | "wsl2" | "metal_sandbox"
  bool is_laptop = 11;
  float benchmark_score_ac = 12;              // see 2.2a, run while plugged in
  float benchmark_score_battery = 13;         // see 2.2a, run while unplugged
}

message RegistrationStatus {
  bool accepted = 1;
  string reason = 2;               // populated iff accepted = false
  string assigned_display_name = 3; // deduplicated hostname for dashboard
  int32 heartbeat_interval_ms = 4;  // server-dictated cadence, see 2.6
  string worker_token = 5;          // persisted by worker, replaces PIN on future reconnects
}

message UnregisterRequest {
  string worker_uuid = 1;
  string reason = 2; // "user_shutdown" | "sleep" | "manual_disconnect"
}
message UnregisterAck { bool acknowledged = 1; }

// ---- Pairing (first-time trust establishment) ----

message PairingRequest {
  WorkerInfo worker_info = 1;
}
message PairingChallenge {
  string pairing_id = 1;
  int64 expires_at_ms = 2;   // pairing_id + PIN valid for 120s, see 2.3a
}
message PairingConfirmation {
  string pairing_id = 1;
  string pin = 2;             // 4 digits, typed by the laptop's owner
}

message UnpairRequest {
  string worker_uuid = 1;
  string initiated_by = 2;   // "worker" | "master" — see 2.4a
}
message UnpairAck { bool acknowledged = 1; }

// ---- Task dispatch ----

message TaskPayload {
  string subtask_id = 1;
  string job_id = 2;
  string binary = 3;          // e.g. "/usr/bin/ffmpeg"
  string args_template = 4;   // "-i {input_chunk} -c:v libx265 -crf 28 {output_chunk}"
  string input_path = 5;      // path ON THE SHARED MOUNT, see Data Plane section
  string output_path = 6;     // path ON THE SHARED MOUNT
  map<string, string> env = 7;
  int32 timeout_seconds = 8;
  ResourceConstraints constraints = 9;
}

message ResourceConstraints {
  float min_vram_gb = 1;
  bool require_gpu = 2;
  bool is_apple_usable = 3;
}

message TaskAck {
  bool accepted = 1;
  string reason = 2;         // populated iff accepted = false, e.g. "vram_unavailable"
  int64 accepted_at_ms = 3;
}

message CancelRequest { string subtask_id = 1; string reason = 2; }
message CancelAck { bool acknowledged = 1; }

message SubTaskResult {
  string subtask_id = 1;
  string job_id = 2;
  bool success = 3;
  string error_message = 4;    // populated iff success = false
  string output_path = 5;      // where the Master should look on the shared mount
  string md5_checksum = 6;     // Master verifies this before aggregation, see 4.6
  int64 started_at_ms = 7;
  int64 finished_at_ms = 8;
}
message ResultAck { bool acknowledged = 1; }

// ---- Telemetry stream ----

message NodeHealth {
  string worker_uuid = 1;
  float cpu_usage_pct = 2;
  float ram_available_gb = 3;
  float vram_available_gb = 4;
  bool user_active = 5;
  int32 core_temp_c = 6;
  int64 timestamp_ms = 7;
  string active_subtask_id = 8; // "" if idle
  PowerState power_state = 9;
  int32 battery_pct = 10;       // -1 if power_state = AC or no battery reported
  bool lid_closed = 11;
  float disk_available_gb = 12; // free space on the shared-mount volume, see 4.7

  enum PowerState {
    UNKNOWN = 0;
    AC = 1;
    BATTERY = 2;
  }
}

message ControlSignal {
  string subtask_id = 1;
  SignalType type = 2;
  enum SignalType {
    UNSPECIFIED = 0;
    THROTTLE = 1;   // set nice 19 / IDLE_PRIORITY_CLASS
    RESUME = 2;     // restore normal priority
    ABORT = 3;      // SIGSTOP-then-kill, see 2.7
  }
}
```

### 2.2a Dual-mode hardware benchmark (runs once, at first pairing)

Because target hardware is student-owned laptops rather than fixed desktops, a single benchmark score is misleading — a laptop's real throughput on battery (thermal/power limited) can be well below its plugged-in throughput. On first pairing, before `benchmark_score_ac`/`benchmark_score_battery` are populated, the worker agent runs a short fixed workload (a small FFmpeg encode) twice:

1. Once with the worker prompting "please plug in your charger" and confirming `power_state = AC` via the OS power API before starting.
2. Once with the worker confirming `power_state = BATTERY`.

Both scores are sent once in `HardwareProfile` at pairing time and are static thereafter — they are not re-measured on every reconnect, only re-triggered if the worker agent detects a hardware change (e.g., a different battery reporting drastically different capacity, or a fresh install). The Matchmaker's scoring formula (§4.5 of the design doc) selects `benchmark_score_ac` or `benchmark_score_battery` at scheduling time based on the node's **current** `NodeHealth.power_state`, not a static value — so a node scores lower for new work the moment it's unplugged, without needing a full re-benchmark.

### 2.3 RPC: `InitiatePairing` / `ConfirmPairing` (first-time trust establishment)

**Why a PIN instead of a pre-shared cluster secret or no auth at all:** the trust model here is "a friend is physically lending you their laptop," not an open volunteer pool and not a single owner's own devices. A pre-shared secret configured once by the Master's operator would need to be communicated out-of-band anyway (told to the friend) — a short-lived PIN is that same communication, formalized, with the added property that it expires and can't be reused to silently re-pair a laptop the owner has since taken back.

**Flow:**

1. Worker (new `worker_uuid`, no locally-stored `worker_token`) calls `InitiatePairing(PairingRequest{worker_info})`.
2. Master creates a pending-pairing entry, generates a random 4-digit PIN (`0000`–`9999`, rejecting `0000`/`1234`/repeated-digit PINs to avoid the laziest guesses), and displays it on the Master's own console/dashboard — e.g. *"fedora-workstation (new) wants to join. Tell them the PIN: 7042."* It returns `PairingChallenge{ pairing_id, expires_at_ms }` to the worker — note the PIN itself is never sent to the worker over the network; it must travel via the human channel (the Master's operator speaking to the laptop's owner), which is what makes this a physical-proximity-consent check rather than just another shared secret sitting on disk.
3. The Master's operator tells the friend the PIN out loud (or shows it on-screen if they're in the same room, which is the assumed common case for this use case).
4. The friend types the PIN into the worker agent's tray-icon prompt. The worker calls `ConfirmPairing(PairingConfirmation{pairing_id, pin})`.
5. If the PIN matches and hasn't expired (120s TTL, single-use), the Master returns `RegistrationStatus{accepted: true, worker_token: "<opaque persisted token>"}`. The worker persists `worker_token` alongside its `worker_uuid` in the same local file (§1.2). All future `RegisterWorker` calls include this token; the Master rejects a `RegisterWorker` carrying a `worker_uuid` it has never `ConfirmPairing`'d, forcing it back through the pairing flow.

**Example — `InitiatePairing` response:**
```json
{ "pairing_id": "9c2f-pending-01", "expires_at_ms": 1754643120000 }
```

**Example — `ConfirmPairing` request (friend just typed "7042"):**
```json
{ "pairing_id": "9c2f-pending-01", "pin": "7042" }
```

**Example — `ConfirmPairing` response (success):**
```json
{ "accepted": true, "reason": "", "assigned_display_name": "fedora-workstation", "heartbeat_interval_ms": 2000, "worker_token": "wtok_3f8e...c1a0" }
```

**Failure modes:** wrong PIN → `accepted: false, reason: "pin_mismatch"` (Master should rate-limit to 5 attempts per `pairing_id` before invalidating it, to stop brute-forcing 4 digits over the LAN); expired PIN → `reason: "pairing_expired"`, worker must call `InitiatePairing` again to get a fresh PIN.

### 2.4 RPC: `RegisterWorker`

**Called by:** Worker, on every subsequent boot after the initial `ConfirmPairing`, presenting the persisted `worker_token` inside `WorkerInfo` (add a `worker_token` field to `WorkerInfo` alongside `worker_uuid` for this purpose). No PIN re-entry required.
**Semantics:** Unary request/response. This is the point at which the Master's Node Registry gains an entry; a worker MUST NOT call `StreamTelemetry` before this returns `accepted = true`. A `RegisterWorker` call presenting an unrecognized or mismatched token is rejected with `reason: "not_paired"` and the worker must fall back to `InitiatePairing`.

**Request example:**
```json
{
  "worker_uuid": "8f14e45f-ceea-4a3d-8f1b-3d2f6a1c9b90",
  "hostname": "fedora-workstation",
  "os_type": "linux",
  "os_version": "Fedora 44 (6.9.14)",
  "hardware": {
    "cpu_model": "Intel Core i5-13500H",
    "cpu_cores_physical": 12,
    "cpu_cores_logical": 16,
    "cpu_instruction_sets": ["AVX2", "AVX-512"],
    "ram_total_gb": 16,
    "has_gpu": false,
    "gpu_model": "",
    "vram_total_gb": 0,
    "hw_encoders": ["QuickSync"],
    "virtualization_mode": "podman"
  }
}
```

**Response example (accepted):**
```json
{
  "accepted": true,
  "reason": "",
  "assigned_display_name": "fedora-workstation",
  "heartbeat_interval_ms": 2000
}
```

**Response example (rejected — duplicate hostname collision on the dashboard, non-fatal but forces disambiguation):**
```json
{
  "accepted": true,
  "reason": "",
  "assigned_display_name": "fedora-workstation-2",
  "heartbeat_interval_ms": 2000
}
```

**Why `heartbeat_interval_ms` is server-dictated, not worker-chosen:** the Master needs to tune telemetry cadence against how many workers are currently connected — 3 workers at 500ms is fine, 40 workers at 500ms floods the Master's event loop. Centralizing the decision means the Master can throttle cadence cluster-wide without touching worker code.

### 2.4a RPC: `UnpairWorker` (revocation) and Master identity persistence

**Revocation.** Pairing (§2.3) has no expiry by design — a friend shouldn't have to re-approve every session — which means there must be an equally simple way to undo it. Either side can call `UnpairWorker`:

- **Worker-initiated** (`initiated_by: "worker"`): the friend clicks "stop sharing this laptop" in the tray app. The worker deletes its local `worker_token` and calls `UnpairWorker` so the Master also drops the token server-side (not strictly required for the worker's own protection, but prevents the Master's dashboard from showing a phantom "paired" device that will never reconnect).
- **Master-initiated** (`initiated_by: "master"`): the Master's operator removes a device from the dashboard's node list (e.g., they got their laptop back and it's leaving the room). The Master invalidates the token server-side immediately; the next `RegisterWorker` or `StreamTelemetry` call from that worker is rejected with `reason: "not_paired"`, at which point the worker agent should surface this to the user and fall back to requiring a fresh `InitiatePairing`/PIN if they want to rejoin later.

`UnpairWorker` should also be called automatically by any currently-active subtask cleanup — i.e., unpairing a worker that has a task in flight must trigger the same fault re-queue path as an `UNREACHABLE` timeout (§4.5), not leave the fragment silently stuck.

**Master identity persistence.** Since a `worker_token` is meaningful only in the context of a specific Master (the same laptop might be paired to two different friends' Masters on different occasions), the Master persists its own `master_uuid` locally the same way a worker persists `worker_uuid` (§1.2) — regenerating it on every restart would silently orphan every existing pairing. A `worker_token` is therefore scoped to `(worker_uuid, master_uuid)`, not global; a worker can hold multiple tokens simultaneously if it has, at different times, been lent to more than one Master.

### 2.5 RPC: `UnregisterWorker`

Called on graceful shutdown (SIGTERM handler / Windows service stop / system sleep event). This exists as a distinct RPC rather than relying purely on heartbeat timeout because a graceful unregister lets the Master immediately re-queue any subtask that node was running (§4.5), instead of waiting out the 3-cycle timeout — shaving up to 6 seconds off recovery for the common case (user closes their laptop) versus the uncommon case (network cable yanked, which genuinely has no graceful signal and must fall back to timeout detection, see §2.7).

### 2.6 RPC: `SubmitSubTask` / `ReportSubTaskResult` / `CancelSubTask`

- `SubmitSubTask` is called **Master → Worker**. It is fire-and-forget from the Matchmaker's perspective except for the immediate `TaskAck` — actual completion arrives later via `ReportSubTaskResult`. Two separate messages (accept-ack vs. result) rather than one blocking call, because a video-encode subtask can run for minutes; holding a unary RPC open for minutes fights with gRPC's default deadlines and load balancer idle-timeouts, and gives no way for the worker to proactively push a `CancelRequest` in between.
- `ReportSubTaskResult` includes `md5_checksum` computed by the worker over the output file **before** it notifies the Master — the Master re-verifies this checksum against the file it reads off the shared mount (§4.6), catching both transmission corruption and premature/partial writes.
- `CancelSubTask` is **Worker-initiated** in the proto (worker asking the master to cancel, e.g. after detecting local resource exhaustion) — the reverse direction (Master telling Worker to cancel) is instead expressed as a `ControlSignal.ABORT` on the telemetry stream (§2.7), not a second RPC, because the Master already has that channel open and it avoids a second connection just to deliver a one-way instruction.

**`TaskAck` rejection example** (worker self-vetoes despite being matched by the scheduler — e.g. VRAM was consumed by a user-launched app between the last telemetry tick and task dispatch):
```json
{ "accepted": false, "reason": "vram_unavailable", "accepted_at_ms": 0 }
```
On rejection, the Master must NOT mark the subtask failed — it re-enters the Matchmaker's pending queue immediately (same code path as a fault-detected re-queue, §4.5), because a `TaskAck` rejection is an expected, non-exceptional race condition, not a fault.

### 2.7 RPC: `StreamTelemetry` (bidirectional stream)

**Cadence:** Worker sends one `NodeHealth` message every `heartbeat_interval_ms` (from RegistrationStatus, default 2000ms in a small cluster).

**Fault detection rule:** the Master marks a worker `UNREACHABLE` after **3 consecutive missed intervals** (i.e., `3 × heartbeat_interval_ms`, ≈6s at default cadence) — this number is not arbitrary: 1 miss is too aggressive (a single GC pause or brief CPU spike on the Master shouldn't fail a healthy node), while 5+ misses delays fault recovery long enough to be visible to a user waiting on a video render. 3 was chosen as the point where transient jitter is filtered out but true failures are caught within one dashboard-refresh cycle.

**Example `NodeHealth` frame:**
```json
{
  "worker_uuid": "8f14e45f-ceea-4a3d-8f1b-3d2f6a1c9b90",
  "cpu_usage_pct": 42.5,
  "ram_available_gb": 9.2,
  "vram_available_gb": 0,
  "user_active": false,
  "core_temp_c": 68,
  "timestamp_ms": 1754643021000,
  "active_subtask_id": "b7e2f1a0-...-subtask-2"
}
```

**Example `ControlSignal` frame (Master → Worker on the same stream):**
```json
{ "subtask_id": "b7e2f1a0-...-subtask-2", "type": "THROTTLE" }
```

### 2.8 `ControlSignal` semantics on the worker

| Signal | Worker action |
|---|---|
| `THROTTLE` | Set process priority to `nice 19` (Linux/macOS) or `IDLE_PRIORITY_CLASS` (Windows); pin execution to a single efficiency core if the CPU topology exposes one. Do NOT stop the process — throttling must be reversible without losing render/encode progress. |
| `RESUME` | Restore normal scheduling priority and core affinity. |
| `ABORT` | Send `SIGSTOP` first (Linux) or suspend the process (Windows `NtSuspendProcess`), holding for up to 500ms to flush any in-flight write, then terminate the Podman container. `SIGSTOP`-before-kill rather than an immediate `SIGKILL` exists specifically to avoid leaving a half-written output fragment on the shared mount that could pass a stale checksum later. |

**Power-state triggers, independent of any `ControlSignal` from the Master:** unlike input-activity throttling (which is a Master decision made from telemetry), power-state reactions are handled **locally and immediately** by the worker, without waiting on a round-trip:

- **On battery unplug (`AC → BATTERY`):** the worker immediately reports the transition on the next `NodeHealth` frame (do not wait for the normal heartbeat interval — send it out-of-cadence) and locally downgrades its own priority the same way a `THROTTLE` signal would, on the assumption that a suddenly-unplugged laptop is about to be picked up and moved. The Master, seeing `power_state = BATTERY` on its next scoring pass, will simply stop assigning *new* work to that node (via `benchmark_score_battery`, §2.2a) rather than force-evacuating an already-running task — abrupt eviction on unplug alone would be more disruptive than useful, since plenty of unplug events are just "walking to the next lecture room," not "closing the lid."
- **On lid close (`lid_closed = true`):** treated as a hard signal, not a soft one — the worker acts exactly like an `ABORT` (checkpoint-unfriendly workloads like FFmpeg are killed cleanly per the `SIGSTOP`-then-kill sequence above) because a closed lid usually means immediate suspend is seconds away, too little time for a graceful Master round-trip.
- **Sleep inhibition while a task is active:** the worker agent holds a platform sleep-inhibit lock for the duration of any active subtask, so the OS doesn't suspend the machine mid-render out from under a task the owner explicitly isn't touching: `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` on Windows, `IOPMAssertionCreateWithName` (equivalent to shelling out to `caffeinate -s`) on macOS, `systemd-inhibit --what=sleep` (or the `org.freedesktop.login1.Inhibit` D-Bus call directly) on Linux. The inhibitor is released the instant the subtask ends or is aborted — it must never persist across idle periods, since permanently blocking sleep would itself be exactly the kind of owner-hostile behavior this project is trying to avoid.

**Every locally-initiated abort MUST be paired with an immediate report to the Master.** A worker that kills a subtask on its own initiative (lid-close, local resource exhaustion, sleep-inhibit denial) must call `ReportSubTaskResult{success:false, error_message:"local_abort_<reason>"}` (or `CancelSubTask`) in the same code path as the kill itself — not rely on the Master noticing via the missed-heartbeat timeout (§2.7). Without this, a lid-close reaction that's instant on the worker side still costs the Master up to 6 seconds before it re-queues the fragment, which defeats the entire purpose of reacting locally in the first place.

**GPU-bound tasks cannot be gently throttled.** `THROTTLE`'s OS-priority mechanism (`nice`/`IDLE_PRIORITY_CLASS`) only affects CPU scheduling. For a GPU-bound subtask (Ollama inference, NVENC-accelerated encode), the GPU driver's own scheduler is unaffected by process priority, so a "throttled" GPU task can still cause visible stutter in a friend's foreground game or video call. There is no cross-vendor, non-invasive way to rate-limit GPU work from outside the driver. Given that, the Matchmaker should treat `ResourceConstraints.require_gpu = true` subtasks as **ABORT-and-migrate on `user_active`**, not `THROTTLE` — i.e., skip the gentle path entirely for GPU work and fall straight to full suspend/migrate the moment the owner is detected as active. Document this as a known asymmetry between CPU and GPU tasks rather than something the throttling model actually solves for GPU work.

## 3. Client API (REST + WebSocket)

### 3.1 Why REST/WebSocket instead of gRPC for the Client tier

The Client Tier is a Python dashboard rendered in a browser-facing or desktop UI context. REST+JSON was chosen over gRPC here specifically because:
- Browser-native `fetch`/`EventSource` support REST and WebSocket with zero extra tooling; gRPC-Web requires a proxy layer (Envoy) that adds an operational dependency this project explicitly tries to avoid (see "Zero-Configuration" design philosophy in the architecture doc).
- The client traffic pattern is low-frequency, human-triggered actions (submit job, check status) — the throughput/multiplexing advantages that justify gRPC on the Master↔Worker plane don't apply here.

Base URL: `http://<master_ip>:8080/api/v1`

### 3.2 `POST /jobs` — Submit a job

**Request body:**

| Field | Type | Required | Description |
|---|---|---|---|
| `name` | string | yes | Human-readable job name. |
| `input_path` | string | yes | Path on the shared mount (see §4.1) to the source asset. |
| `output_path` | string | yes | Path on the shared mount for the final merged result. |
| `workflow` | object | yes | Inline workflow manifest — same schema as `workflow.yaml` (§4 below), submitted as JSON rather than requiring a file upload, so the dashboard can construct it from form fields. |

**Example request:**
```http
POST /api/v1/jobs
Content-Type: application/json

{
  "name": "Vacation-4K-to-H265",
  "input_path": "/mnt/cluster-share/incoming/vacation.mkv",
  "output_path": "/mnt/cluster-share/outgoing/vacation_h265.mkv",
  "workflow": {
    "constraints": { "resource_preference": "gpu", "is_apple_usable": true, "min_vram_gb": 4 },
    "fragmentation": { "method": "timestamp_split" },
    "execution": {
      "binary": "/usr/bin/ffmpeg",
      "args": "-i {input_chunk} -c:v libx265 -crf 28 {output_chunk}"
    }
  }
}
```

**Response `202 Accepted`:**
```json
{
  "job_id": "3f9c1e2a-4b5d-4e6f-8a9b-0c1d2e3f4a5b",
  "status": "QUEUED",
  "created_at_ms": 1754643000000,
  "status_url": "/api/v1/jobs/3f9c1e2a-4b5d-4e6f-8a9b-0c1d2e3f4a5b"
}
```
`202`, not `201`, is used deliberately: the job resource is accepted but fragmentation/scheduling hasn't happened yet, so there is not yet a fully-formed resource to return a `Location` header for in the `201` sense — `202` correctly communicates "accepted for async processing."

**Error responses:**
| Status | Body | Cause |
|---|---|---|
| `400` | `{ "error": "invalid_workflow", "detail": "..." }` | Schema validation failed (see §4 for required fields) |
| `404` | `{ "error": "input_not_found" }` | `input_path` doesn't exist on the shared mount at submission time |
| `503` | `{ "error": "no_eligible_nodes" }` | No registered worker currently satisfies the workflow's `constraints` |

### 3.3 `GET /jobs/{job_id}` — Job status

**Response `200`:**
```json
{
  "job_id": "3f9c1e2a-4b5d-4e6f-8a9b-0c1d2e3f4a5b",
  "name": "Vacation-4K-to-H265",
  "status": "RUNNING",
  "created_at_ms": 1754643000000,
  "started_at_ms": 1754643004000,
  "estimated_single_node_time_s": 1440,
  "fragments": [
    { "subtask_id": "sub-1", "assigned_node": "fedora-workstation", "status": "COMPLETED", "duration_s": 570 },
    { "subtask_id": "sub-2", "assigned_node": "win11-rtx3060", "status": "RUNNING", "duration_s": null }
  ]
}
```
`status` is one of: `QUEUED`, `FRAGMENTING`, `RUNNING`, `AGGREGATING`, `COMPLETED`, `FAILED`, `CANCELLED`.

### 3.4 `DELETE /jobs/{job_id}` — Cancel a job

Cascades to a `ControlSignal.ABORT` (§2.7) on every worker currently holding a subtask for this job. Returns `202` immediately; actual worker-side termination is async and reflected in the next `GET /jobs/{job_id}` status poll.

### 3.5 `GET /jobs/{job_id}/stream` — Live progress (WebSocket)

Upgrades to WebSocket. The Master pushes a JSON frame identical in shape to §3.3's fragment list every time a fragment's status changes (event-driven push, not polling — chosen because a video render dashboard re-drawing a progress bar on a fixed poll interval either lags visibly or wastes requests; push gives immediate UI feedback the moment a chunk finishes, matching what the CLI reference implementation prints to console).

**Example frame:**
```json
{ "event": "fragment_completed", "subtask_id": "sub-1", "assigned_node": "fedora-workstation", "duration_s": 570 }
```

### 3.6 `GET /nodes` — List cluster nodes

**Response `200`:**
```json
{
  "nodes": [
    {
      "worker_uuid": "8f14e45f-...",
      "display_name": "fedora-workstation",
      "os_type": "linux",
      "status": "ONLINE",
      "user_active": false,
      "cpu_usage_pct": 12.0,
      "vram_available_gb": 0,
      "last_heartbeat_ms": 1754643021000
    }
  ]
}
```
`status` is one of `ONLINE`, `BUSY`, `UNREACHABLE` — this is the REST-facing simplification of the raw `NodeHealth` telemetry; the dashboard doesn't need raw temperature/instruction-set data, so the Master intentionally projects a smaller surface here rather than passing the full internal `NodeHealth` schema through, keeping the client contract decoupled from internal telemetry schema changes.

### 3.7 `GET /health` — Master liveness

Returns `200 {"status":"ok","uptime_s":N}` unconditionally if the process is up. Used by the dashboard to distinguish "Master is down" from "Master is up but no nodes are online" — two failure modes that otherwise look identical from `GET /nodes` returning an empty list.

## 4. Data Plane Contract (SMB/NFS Shared Storage)

### 4.1 Why a shared mount instead of streaming file bytes over gRPC

Video/AI payloads are multi-gigabyte. Streaming them as gRPC message chunks would require: (a) manual chunking logic duplicated on both sides, (b) holding the file in memory or a temp buffer during transfer, and (c) paying the transfer cost **twice** — once to send the chunk, once for the worker to write it to disk before Podman can mount it as a volume. A shared SMB/NFS volume collapses this to zero extra copies: the Master writes once, the worker's container bind-mounts the same path directly. The explicit design tradeoff accepted: this requires all nodes to have network access to a common share (one extra one-time setup step), in exchange for eliminating the dominant cost in every job — large-file movement — from the RPC layer entirely.

### 4.2 Directory layout (convention, enforced by the Master at startup)

```
<shared_root>/
  incoming/            # client-submitted source assets
  jobs/<job_id>/
    chunks/            # input fragments written by Master's fragmentation engine
    results/           # raw output fragments written by workers
  outgoing/            # final aggregated output, written by the Master
```

### 4.3 Path fields on the wire

`TaskPayload.input_path` and `TaskPayload.output_path` (§2.2) are **absolute paths as seen from inside the mount**, e.g. `/mnt/cluster-share/jobs/<job_id>/chunks/chunk_1.mkv`. The Master does not send raw bytes; it sends a path, and expects every worker to have that same path resolvable. Windows workers resolve this via a WSL2 bind of the SMB share to the same POSIX-style path so `args_template` substitution doesn't need per-OS path branching.

### 4.4 Write-then-notify ordering

A worker MUST complete and `fsync()` its output file write **before** calling `ReportSubTaskResult`. This ordering constraint exists because the Master may begin the checksum-verify step the instant it receives the RPC — if the notify races the write, the Master reads a truncated file and produces a false corruption failure.

### 4.5 Fault re-queue path

When the Master marks a worker `UNREACHABLE` (§2.6) or receives an `UnregisterWorker` mid-task, any subtask whose `active_subtask_id` pointed at that worker is moved from the Master's in-memory `ACTIVE` map back to `PENDING`, and re-submitted to the Matchmaker's next scoring pass. Partial output files left by the dead worker in `jobs/<job_id>/results/` are deleted before re-queue, to guarantee the eventual aggregation step never accidentally picks up a stale partial fragment with a coincidentally-matching filename.

### 4.6 Integrity check

On `ReportSubTaskResult`, the Master computes MD5 over the file at `output_path` and compares it to `SubTaskResult.md5_checksum`. MD5 (not SHA-256) is deliberate here: this check is defending against transmission/write corruption on a trusted LAN, not an adversarial actor, so cryptographic collision-resistance is not the requirement — MD5's speed advantage matters more when this runs on every fragment of a large job.

### 4.7 Disk-space awareness

Unlike a dedicated server, a friend's laptop has finite, often already-tight local storage, and the shared mount lives on it or on a device they control — an unmonitored `jobs/<job_id>/chunks`/`results` tree filling their disk is one of the most plausible real failure modes for this project's actual target use case.

- `NodeHealth.disk_available_gb` (§2.2) is reported on every heartbeat for the volume backing the shared mount.
- The Matchmaker filters out (does not merely deprioritize) any node whose `disk_available_gb` is below the input chunk size plus a fixed safety margin (recommend: chunk size × 1.5, to leave room for the output fragment alongside the input) before it is eligible for a `SubmitSubTask` dispatch — this is a hard constraint, not part of the weighted score, because running out of disk mid-write is a worse failure than picking a slightly slower node.
- **Retention:** once `ReportSubTaskResult` succeeds and the Master's Integrity Verifier (§4.6) confirms the checksum, the Master deletes the corresponding input chunk from `jobs/<job_id>/chunks/` immediately (it's no longer needed). The full `jobs/<job_id>/` directory (chunks + results) is deleted once the job reaches `COMPLETED` or `FAILED` status and the final output has been confirmed written to `outgoing/` — not kept indefinitely "just in case." A job's raw fragments should never outlive the job itself on a borrowed machine.

## 5. Security Notes

### 5.1 Threat model, explicitly

This system is scoped for **known-friend, physically-present device lending** (e.g., a hostel-mate's laptop), not an open volunteer pool of strangers and not a corporate multi-tenant environment. That scoping is what justifies a 4-digit PIN instead of TLS/mTLS + certificate management — the PIN's job is to prove the laptop's owner was physically present and consented at pairing time, not to resist a dedicated attacker. Document this scoping explicitly in the report; it's a deliberate, defensible tradeoff, not an omission, as long as it's stated.

### 5.2 What the pairing flow (§2.3) does and doesn't protect against

- **Protects against:** a stranger on the same hotspot silently registering as a worker and having arbitrary binaries executed on their machine without their knowledge — `ConfirmPairing` requires someone physically at the worker to type a PIN they were told out-of-band.
- **Protects against:** a previously-unpaired device replaying an old `worker_uuid` to impersonate a laptop that already left the cluster — the Master only trusts a `RegisterWorker` call carrying the exact `worker_token` issued at that device's own `ConfirmPairing`.
- **Does NOT protect against:** a compromised Master pushing a malicious `args_template`/`binary` to an already-paired worker — pairing establishes *device* trust once, it does not sandbox *task content* on every dispatch. If this project is extended beyond the "run FFmpeg/Blender/Ollama with a fixed set of known binaries" model, restrict `TaskPayload.binary` (§2.2) to an allow-list on the worker side rather than trusting whatever the Master sends.
- **Does NOT protect against:** eavesdropping or tampering in transit — gRPC and the REST API run unencrypted (plain HTTP/2 and HTTP) by default in this design. On a personal hotspot this is a reasonable risk to accept for a student project; call it out as a known limitation rather than silently shipping it.

### 5.3 REST API (Client tier)

The REST API (§3) still has no auth of its own. Given the scoping above (one person running the Master, deciding which friends to pair), this is lower-risk than the worker-registration gap was — but it's still worth noting in the report as a limitation rather than leaving it unaddressed, since anyone who can reach port `8080` can submit or cancel jobs.

### 5.4 Worker onboarding

Not a wire protocol concern, but a prerequisite for the pairing flow to make sense in the report: the worker agent should be distributed as a single portable executable (no installer, no admin/root privileges required to run) — matching the "borrow a friend's laptop for an afternoon" use case, where asking them to sit through a full install is friction the design otherwise goes out of its way to avoid. State this explicitly as a non-functional requirement alongside the existing "<50MB idle RAM" constraint.

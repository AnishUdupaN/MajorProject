# LAN-Based Distributed Compute System — API Reference (Revised Edition)

**Scope:** This document specifies the complete network-facing and process-facing interface for the LAN-Based Distributed Compute System, optimized for small-scale, friend-to-friend compute sharing in classroom and hostel environments over Android hotspots. All protocols are designed around Python-native tooling (FastAPI, HTTP/JSON, WebSocket) to eliminate compilation dependencies and simplify debugging over consumer-grade Wi-Fi.

**Target Environment:**
- **Master Node:** Your laptop running the orchestrator and file server.
- **Worker Nodes:** 3–10 friends' laptops (Windows 11 with WSL2, Linux native, macOS native app).
- **Network:** Android mobile hotspot (single flat subnet, no routing).
- **Trust Model:** Known-friend, physically-present device lending. No incentives, no fairness scheduling — only constraint is "do not hinder the laptop owner's performance."

---

## 0. Global Conventions

- **Default ports:**
  - UDP Discovery: `5005`
  - FastAPI Control Plane: `8000`
  - HTTP File Server (sender.py): `8080`
  - Client Dashboard (optional): `8000` (served by same FastAPI app)
- **IDs:** All entity IDs (`job_id`, `subtask_id`, `worker_uuid`) are UUIDv4 strings.
  - `job_id` / `subtask_id`: Generated by the Master.
  - `worker_uuid`: Generated once by the Worker on first install, persisted at:
    - Linux/WSL2: `~/.lan-compute/worker_id`
    - Windows (native): `%APPDATA%\lan-compute\worker_id`
    - macOS: `~/Library/Application Support/lan-compute/worker_id`
- **Timestamps:** Unix epoch milliseconds (integers, UTC). Used for telemetry, PIN expiry, and heartbeat math.
- **Encoding:** All payloads are UTF-8 JSON. No Protobuf, no binary framing.
- **Versioning:** REST routes are prefixed `/api/v1/...`. Bump version segment on breaking changes.
- **CLI-First Philosophy:** The primary user interface is the CLI (`taskrunner.py`). The REST API exists for optional dashboard usage and programmatic access, but all core functionality must be drivable from the command line without a browser.

## 1. Discovery Protocol (UDP Broadcast)

### 1.1 Design Rationale

UDP broadcast is retained over mDNS/Zeroconf for three reasons:
1. **Android hotspot compatibility:** mDNS reflectors do not exist on Android hotspots. Raw UDP broadcast to `255.255.255.255` works reliably on the single flat subnet.
2. **Zero OS dependencies:** Requires only a UDP socket — no Avahi, Bonjour, or Windows mDNS responder services.
3. **Custom payload:** The first packet carries full hardware capabilities as JSON, allowing the Master to pre-filter before any TCP handshake.

**Tradeoff accepted:** UDP broadcast does not cross subnet boundaries. This is acceptable because the explicit design target is a single Android hotspot (single `/24` or `/16` subnet).

### 1.2 Android Hotspot Specifics

On Android hotspots:
- The gateway IP is typically `192.168.43.1` or `172.20.10.1`.
- DHCP leases are short; workers may receive new IPs on each reconnect.
- The Master must bind its HTTP servers to `0.0.0.0` because hotspot interfaces are treated as "Public" by OS firewalls.
- Workers must **not** hardcode the Master IP. Instead, they broadcast to `255.255.255.255:5005` and accept the `MASTER_OFFER` from whichever source IP responds.

### 1.3 Message — `DISCOVERY_BEACON` (Worker → Master)

- **Direction:** Broadcast to `255.255.255.255:5005`.
- **Frequency:** Sent once on startup, then every 5s until `MASTER_OFFER` received. If the worker loses its HTTP/WebSocket connection to the Master, it re-enters beacon mode automatically.

**Payload schema:**

| Field | Type | Required | Description |
|---|---|---|---|
| `type` | string | yes | Always `"DISCOVERY_BEACON"`. |
| `protocol_version` | int | yes | `1`. Master rejects unsupported versions and logs a warning. |
| `worker_uuid` | string (UUID) | yes | Persisted locally. Survives restarts so the Master recognizes returning nodes. |
| `local_ip` | string | yes | Best-guess LAN IP from the UDP socket. Do NOT use `socket.gethostname()`. |
| `os_type` | enum string | yes | `"windows"`, `"linux"`, or `"macos"`. |
| `hostname` | string | no | Human-readable. Falls back to `worker_uuid[:8]` if omitted. |

**Example packet:**
```json
{
  "type": "DISCOVERY_BEACON",
  "protocol_version": 1,
  "worker_uuid": "8f14e45f-ceea-4a3d-8f1b-3d2f6a1c9b90",
  "local_ip": "192.168.43.102",
  "os_type": "linux",
  "hostname": "fedora-workstation"
}
```

### 1.4 Message — `MASTER_OFFER` (Master → Worker, unicast)

Sent as a unicast UDP reply to the source IP:port of the beacon.

| Field | Type | Required | Description |
|---|---|---|---|
| `type` | string | yes | `"MASTER_OFFER"` |
| `protocol_version` | int | yes | Must match beacon's version. |
| `master_uuid` | string (UUID) | yes | Identifies this Master instance. |
| `fastapi_uri` | string | yes | e.g. `"http://192.168.43.1:8000"`. Explicitly sent because the UDP listener IP may differ from the HTTP bind IP on multi-homed machines. |
| `file_server_uri` | string | yes | e.g. `"http://192.168.43.1:8080/files"`. Base URL for the sender.py HTTP file server. |
| `cluster_token` | string | no | Optional shared secret. Empty string for default trusted-LAN mode. |

**Example packet:**
```json
{
  "type": "MASTER_OFFER",
  "protocol_version": 1,
  "master_uuid": "1a2b3c4d-5e6f-7890-abcd-ef1234567890",
  "fastapi_uri": "http://192.168.43.1:8000",
  "file_server_uri": "http://192.168.43.1:8080/files",
  "cluster_token": ""
}
```

### 1.5 Post-Discovery Handoff

Upon receiving a valid `MASTER_OFFER`, the worker immediately:
1. Opens an HTTP session to `fastapi_uri`.
2. Calls `POST /api/v1/workers/pairing/initiate` (§2.3) if never paired before.
3. Calls `POST /api/v1/workers/register` (§2.4) if already paired (has stored `worker_token`).

## 2. Control Plane API (FastAPI)

### 2.1 Why FastAPI/HTTP instead of gRPC

- **Python-native:** Zero compilation steps. `grpcio` frequently breaks on mismatched Python versions or missing MSVC build tools on Windows. FastAPI runs with `pip install fastapi uvicorn`.
- **Debuggability:** On an Android hotspot, debugging a gRPC stream failure requires specialized tools. HTTP/JSON can be inspected with any browser's DevTools or `curl`.
- **Sufficient for scale:** With <10 workers and low-frequency control signals, HTTP/2 multiplexing advantages of gRPC are irrelevant. WebSocket provides bidirectional streaming where needed.
- **File transfer synergy:** The sender.py file server is already HTTP-based. Using HTTP for control + data creates a unified stack.

**Tradeoff:** Slightly higher per-message overhead (~100 bytes of JSON vs. Protobuf binary). At <10 nodes and 2s heartbeat intervals, this is negligible.

### 2.2 Base URL

`http://<master_ip>:8000/api/v1`

### 2.3 First-Time Pairing (PIN-based Trust)

**Why a PIN:** The trust model is "a friend is physically lending you their laptop." A 4-digit PIN proves physical proximity and consent at pairing time. It is not a cryptographic defense against a dedicated attacker — it prevents silent registration by strangers on the same hotspot.

**Flow:**

1. **Initiate Pairing:**
   - `POST /workers/pairing/initiate`
   - Worker sends its full `WorkerInfo` (without `worker_token`).
   - Master generates a random 4-digit PIN (rejecting `0000`, `1234`, and repeated digits like `1111`).
   - Master displays PIN on its CLI/dashboard: *"fedora-workstation wants to join. Tell them PIN: 7042."*
   - Returns `pairing_id` and `expires_at_ms` (300s / 5 minutes TTL).

2. **Confirm Pairing:**
   - `POST /workers/pairing/confirm`
   - Friend types PIN into worker tray app.
   - Worker sends `{pairing_id, pin}`.
   - On match, Master returns `worker_token` (opaque string). Worker persists it locally.

**PIN expiry:** 300 seconds (5 minutes). This accommodates friends who step away briefly. A "resend PIN" button on the Master dashboard can invalidate the old pairing and create a new one.

**Rate limiting:** 5 attempts per `pairing_id`, then invalidation.

**Request/Response Examples:**

`POST /api/v1/workers/pairing/initiate`
```json

  "os_version": "Fedora 44 (6.9.14)",

    "cpu_model": "Intel Core i5-13500H",

    "cpu_cores_logical": 16,
    "cpu_instruction_sets": ["AVX2", "AVX-512"],
    "ram_total_gb": 16,
```

### 2.4 Worker Registration

`POST /api/v1/workers/register`

Called on every subsequent boot. Includes the persisted `worker_token`.

**Single-Master Scope:** A `worker_token` is scoped to exactly one Master (`master_uuid`). If a worker was previously paired to a different Master IP, the old token is overwritten. This eliminates multi-master token complexity — your use case is one Master + N friends.

**Request:**
```json
{
  "worker_uuid": "8f14e45f-ceea-4a3d-8f1b-3d2f6a1c9b90",
  "worker_token": "wtok_3f8e...c1a0",
  "hostname": "fedora-workstation",
  "os_type": "linux",
  "os_version": "Fedora 44 (6.9.14)",
  "hardware": { /* same schema as pairing */ }
}
```

**Response (accepted):**
```json
{
  "accepted": true,
  "assigned_display_name": "fedora-workstation",
  "heartbeat_interval_ms": 2000
}
```

**Response (rejected — token invalid):**
```json
{
  "accepted": false,
  "reason": "not_paired"
}
```

### 2.5 Unpairing and Revocation

`POST /api/v1/workers/unpair`

Either side can initiate. Unpairing a worker with an active subtask triggers immediate fault re-queue (same path as unreachable timeout).

**Request:**
```json
{
  "worker_uuid": "8f14e45f-ceea-4a3d-8f1b-3d2f6a1c9b90",
  "initiated_by": "worker"
}
```

### 2.6 Graceful Unregister

`POST /api/v1/workers/unregister`

Called on graceful shutdown, sleep, or Ctrl+C. Lets the Master immediately re-queue tasks instead of waiting for heartbeat timeout.

**Request:**
```json
{
  "worker_uuid": "8f14e45f-ceea-4a3d-8f1b-3d2f6a1c9b90",
  "reason": "user_shutdown"
}
```

### 2.7 Task Dispatch

`POST /api/v1/workers/{worker_uuid}/tasks`

Master → Worker. Dispatches one subtask for execution.

**Request:**
```json
{
  "subtask_id": "sub-1",
  "job_id": "3f9c1e2a-...",
  "binary": "/usr/bin/ffmpeg",
  "args_template": "-i {input_chunk} -c:v libx265 -crf 28 {output_chunk}",
  "input_url": "http://192.168.43.1:8080/files/jobs/3f9c/.../chunks/chunk_1.mkv",
  "output_url": "http://192.168.43.1:8080/files/jobs/3f9c/.../results/chunk_1.mkv",
  "env": {},
  "timeout_seconds": 3600,
  "constraints": {
    "min_vram_gb": 0,
    "require_gpu": false,
    "is_apple_usable": false
  }
}
```

**Worker-side Binary Allow-List:** Before executing, the worker checks `binary` against a local allow-list:
```yaml
# ~/.lan-compute/allowlist.yaml
allowed_binaries:
  - "/usr/bin/ffmpeg"
  - "/usr/local/bin/ollama"
  - "/Applications/Blender.app/Contents/MacOS/Blender"
```
If the binary is not on the list, the worker rejects the task with `reason: "binary_not_allowed"`. This prevents a compromised Master from executing arbitrary malware on a friend's laptop.

**Response (ack):**
```json
{
  "accepted": true,
  "accepted_at_ms": 1754643000000
}
```

**Response (rejection — e.g. VRAM consumed by user app):**
```json
{
  "accepted": false,
  "reason": "vram_unavailable"
}
```

### 2.8 Task Result Reporting

`POST /api/v1/workers/{worker_uuid}/results`

Worker → Master. Reports terminal state of a subtask.

**Request:**
```json
{
  "subtask_id": "sub-1",
  "job_id": "3f9c1e2a-...",
  "success": true,
  "error_message": "",
  "output_url": "http://192.168.43.1:8080/files/jobs/3f9c/.../results/chunk_1.mkv",
  "md5_checksum": "d41d8cd98f00b204e9800998ecf8427e",
  "started_at_ms": 1754643000000,
  "finished_at_ms": 1754643570000
}
```

**Integrity Check:** The Master downloads the file from `output_url` and verifies MD5 against `md5_checksum`. MD5 is sufficient for LAN corruption detection (not cryptographic security).

### 2.9 Telemetry Stream (WebSocket)

`WS /api/v1/workers/{worker_uuid}/telemetry`

Bidirectional WebSocket connection. Worker pushes `NodeHealth` frames; Master pushes `ControlSignal` frames.

**Cadence:** Worker sends one `NodeHealth` frame every `heartbeat_interval_ms` (default 2000ms).

**Fault Detection:** Master marks worker `UNREACHABLE` after **3 consecutive missed intervals** (~6s at default). 1 miss is too aggressive (GC pause); 5+ misses delay recovery visibly.

**NodeHealth frame:**
```json
{
  "worker_uuid": "8f14e45f-ceea-4a3d-8f1b-3d2f6a1c9b90",
  "cpu_usage_pct": 42.5,
  "ram_available_gb": 9.2,
  "vram_available_gb": 0,
  "user_active": false,
  "core_temp_c": 68,
  "timestamp_ms": 1754643021000,
  "active_subtask_id": "sub-1",
  "power_state": "AC",
  "battery_pct": 85,
  "lid_closed": false,
  "disk_available_gb": 120.5
}
```

**ControlSignal frame (Master → Worker):**
```json
{
  "subtask_id": "sub-1",
  "type": "THROTTLE"
}
```

**Signal Types:**
- `THROTTLE`: Set `nice 19` (Linux/macOS) or `IDLE_PRIORITY_CLASS` (Windows). Pin to a single efficiency core if available. Reversible.
- `RESUME`: Restore normal priority.
- `ABORT`: `SIGSTOP`-then-kill sequence. Wait 500ms between stop and kill to flush in-flight writes.

### 2.10 Power-State Local Reactions (Worker-Initiated)

Unlike input-activity throttling (Master decision from telemetry), power-state reactions are handled **locally and immediately** by the worker:

- **On battery unplug (`AC → BATTERY`):** Worker immediately sends out-of-cadence `NodeHealth` with `power_state: "BATTERY"` and locally downgrades its own priority. The Master stops assigning *new* work (uses `benchmark_score_battery`), but does **not** abort running tasks — unplug events are often temporary (walking to next room).
- **On lid close (`lid_closed: true`):** Treated as hard abort signal. Worker executes `ABORT` sequence immediately and reports `local_abort_lid_closed` to the Master. Closed lid usually means suspend is seconds away.
- **Sleep inhibition:** Worker holds OS sleep-inhibit lock for duration of active subtask:
  - Windows: `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)`
  - macOS: `IOPMAssertionCreateWithName` (equivalent to `caffeinate -s`)
  - Linux: `systemd-inhibit --what=sleep` or D-Bus `org.freedesktop.login1.Inhibit`
  - Released immediately when subtask ends or aborts. Never persist across idle periods.

### 2.11 Battery Threshold Hard Constraint

The Matchmaker filters out (hard constraint, not score penalty) any node where `battery_pct < 20` (configurable). Running out of battery on a borrowed laptop is worse than picking a slower node. The worker also auto-rejects new tasks locally if `battery_pct < 20`.

### 2.12 GPU Task Grace Period

GPU-bound tasks (Ollama inference, NVENC encode) cannot be gently throttled via OS `nice`. However, immediate `ABORT` on `user_active` is disruptive.

**Enhanced Logic:**
1. On `user_active` detected, Master sends `THROTTLE` (CPU-side) and waits **30 seconds**.
2. If user is still active after 30s, Master sends `ABORT`.
3. For Ollama specifically, the worker calls `/api/save` to checkpoint model state before aborting, allowing resume on another node.

This grace period prevents aborting a task because a friend checked a notification.

## 3. File Transfer API (sender.py HTTP Server)

### 3.1 Why HTTP File Server instead of SMB/NFS

- **Android hotspot + Windows:** Windows classifies hotspot networks as "Public," blocking SMB inbound by default. Configuring firewall exceptions on a friend's laptop is friction.
- **Zero configuration:** The Master runs `sender.py`; workers use `requests.get()` / `requests.post()`. No OS-level sharing setup.
- **No double-copy:** Workers download chunks directly to a temp directory, process them, and POST results back. The shared-mount "write once, mount everywhere" model is replaced by explicit HTTP transfer, which is acceptable because chunk sizes are manageable (video segments, not full 10GB files).

### 3.2 sender.py Integration

The Master runs the provided `sender.py` on port `8080`:
```bash
python sender.py /path/to/cluster-share 8080
```

**Directory layout (enforced by Master):**
```
cluster-share/
  jobs/<job_id>/
    chunks/     # Master writes input fragments here
    results/    # Workers POST output fragments here
```

**Worker File Operations:**
- **Download chunk:** `GET http://<master>:8080/files/jobs/<job_id>/chunks/chunk_1.mkv`
- **Upload result:** `POST http://<master>:8080/files/jobs/<job_id>/results/chunk_1.mkv` (multipart/form-data)

**sender.py concurrency limit:** `MAX_CONCURRENT_CONNECTIONS = 16`. If exceeded, returns HTTP 503. Workers retry with exponential backoff.

### 3.3 Write-Then-Notify Ordering

Worker MUST complete and `fsync()` its output file, verify its own MD5, and successfully POST it to the file server **before** calling `POST /api/v1/workers/{uuid}/results`.

### 3.4 Fault Re-Queue and Cleanup

When a worker is marked `UNREACHABLE` or unregisters mid-task:
1. Master moves subtask from `ACTIVE` to `PENDING` queue.
2. Master deletes partial output files from `jobs/<job_id>/results/` to prevent stale fragment pickup.
3. Matchmaker re-evaluates on next scoring pass.

### 3.5 Disk-Space Awareness

`NodeHealth.disk_available_gb` reports free space on the worker's temp directory volume. The Matchmaker filters out nodes where `disk_available_gb < (chunk_size × 1.5)`.

## 5. Worker Implementation by OS

### 5.1 Windows (WSL2 + Podman)

**Rationale:** Target users are techies with WSL2 already installed. Podman in WSL2 provides daemonless containers with near-native CUDA performance via vGPU passthrough.

- **Isolation:** Podman inside WSL2 Ubuntu.
- **GPU Support:** CUDA via WSL2 vGPU.
- **Process Priority:** Windows worker agent sets `IDLE_PRIORITY_CLASS` on the WSL2 VM process itself for throttling, or delegates to `nice` inside WSL2.
- **OS Hooks:** `GetLastInputInfo` via `pywin32` for user presence.
- **Power State:** Windows power APIs (`GetSystemPowerStatus`) for AC/Battery.

### 5.2 Linux (Native Podman)

- **Isolation:** Native Podman (daemonless, rootless).
- **GPU Support:** CUDA or ROCm native.
- **Process Priority:** `nice 19`, `cpulimit`, cgroups v2.
- **OS Hooks:** `/dev/input/` or X11/Wayland idle timers.
- **Power State:** `upower` or `/sys/class/power_supply/`.

### 5.3 macOS (Native Sandboxed App)

- **Isolation:** Sandboxed native application (no containers). Containerized GPU virtualization on macOS is severely limited.
- **GPU Support:** Direct Metal API access.
- **Process Priority:** `nice`, `cputhrottle`.
- **OS Hooks:** `IOKit` (`IOHIDElapsedIdleTime`) for user presence.
- **Power State:** `IOPowerSources` API.

## 6. Matchmaker Scoring Algorithm

### 6.1 Formula

For each node `n` and subtask:
```
Score_n = (CPU_n × w_cpu) + (VRAM_n × w_gpu) - (Latency_n × w_net) + (AC_State_n × w_pwr)
```

- If `user_active = true`: `Score_n = Score_n × 0.2` (aggressive penalty).
- If `core_temp_c > 85`: `Score_n = Score_n × 0.5`.
- If `battery_pct < 20`: Node is filtered out (hard constraint).
- If `power_state = "BATTERY"`: Use `benchmark_score_battery` instead of `benchmark_score_ac`.

### 6.2 Dual-Mode Benchmark

Run once at install time:
1. Prompt user to plug in charger. Run micro-benchmark (small FFmpeg encode). Record `benchmark_score_ac`.
2. Prompt user to unplug. Run same benchmark. Record `benchmark_score_battery`.

Scores are static thereafter. The Matchmaker selects the appropriate score at scheduling time based on current `power_state`.

## 7. Security Notes

### 7.1 Threat Model

This system is scoped for **known-friend, physically-present device lending** on a personal Android hotspot. It is **not** designed for open volunteer pools or corporate multi-tenant environments.

### 7.2 What Pairing Protects Against

- **Protects:** Strangers on the hotspot silently registering as workers.
- **Protects:** Replay of old `worker_uuid` by a device that left the cluster.
- **Does NOT protect:** Compromised Master pushing malicious binaries. Mitigated by worker-side binary allow-list (§2.7).
- **Does NOT protect:** Eavesdropping or tampering in transit. gRPC/REST run over plain HTTP by default. Acceptable risk for personal hotspot; document as known limitation.

### 7.3 REST API Auth

The Client REST API (§4) has no authentication. Given the single-operator model (you run the Master), this is acceptable but should be noted as a limitation.

### 7.4 Worker Distribution

The worker agent should be distributed as a **single portable executable** (PyInstaller) with no installer and no admin/root privileges required. This matches the "borrow a friend's laptop for an afternoon" use case.
